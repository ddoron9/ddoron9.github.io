OpenClaw 같은 로컬 에이전트는 매우 강력하다.
파일 수정, 설정 변경, 서비스 재시작 같은 운영 작업을 빠르게 처리해준다.

문제는 이 편의성이 종종 **사용자 권한과 거의 동일한 실행 권한**으로 이어진다는 점이다.
즉, 에이전트는 단순히 답변하는 챗봇이 아니라, 사용자의 컨텍스트에서 실제 시스템을 바꿀 수 있는 실행 주체가 된다.

핵심 이슈는 성능이 아니라 **권한의 경계와 책임 소재**다.

## 실제로 드러나는 위험 신호

아래 사례는 대화형 인터페이스에서 자주 발생하는 권한 착시를 보여준다.

![Slack thread: allowlist 채널 추가 논의](/assets/images/2026-03-21-openclaw-permission-boundary_001.png)

대화 흐름은 자연스럽다.
"채널 allowlist 추가할까?" → "그럼 restart 하면 되나?" 처럼, 운영자 입장에서는 가벼운 확인처럼 보인다.
하지만 이 순간 실제로는 메시징 권한 표면이 확장되고, 실행 범위가 넓어진다.

![Slack #video 채널 참여 후 호출 화면](/assets/images/2026-03-21-openclaw-permission-boundary_002.png)

채널에 에이전트가 참여한 뒤에는 호출 진입 장벽이 급격히 낮아진다.
권한이 이미 열려 있으면, 사용자 입장에서는 "그냥 멘션하면 되는" 경험이 된다.

![사용자 컨텍스트 권한/파일 수정 가능성 대화](/assets/images/2026-03-21-openclaw-permission-boundary_003.png)

그리고 가장 중요한 지점:
에이전트가 호스트의 사용자 컨텍스트로 실행될 때, 해당 사용자가 접근 가능한 파일/설정은 에이전트도 사실상 동일하게 다룰 수 있다.
이는 생산성을 극대화하지만, 동시에 실수의 반경도 키운다.

## 왜 위험한가

- **권한 상속 리스크**: 에이전트가 호스트 사용자 컨텍스트를 그대로 상속한다.
- **행위의 비가시성**: “도움 요청 → 즉시 실행” 흐름에서 변경 사항 추적이 누락되기 쉽다.
- **채널 확장 리스크**: allowlist 확장이 곧 명령 표면 확대가 된다.
- **신뢰의 착시**: 친숙한 채팅 UI 때문에 실제 권한 수준을 과소평가한다.

## 필요한 가드레일

1. **최소 권한 원칙**
   - 기본은 읽기/제한 모드로 시작
   - 쓰기, 재시작, 외부 전송은 단계적으로 권한 부여

2. **명시적 승인 흐름**
   - 민감 명령 실행 전/후 diff와 영향 범위 표시
   - 승인 이력 보존

3. **채널별 capability 분리**
   - 채널 추가 = 전체 권한 부여가 아니라, 기능 단위 허용

4. **감사 로그 기본화**
   - 누가, 언제, 무엇을, 어떤 경로로 바꿨는지 남겨야 한다.

5. **복구 가능성 확보**
   - 설정 파일 버전 관리
   - 롤백 절차 문서화
   - 안전한 기본값 유지

## 결론

문제의 본질은 “AI가 똑똑한가”가 아니다.

**AI가 어떤 권한으로, 어떤 절차를 거쳐, 누구의 책임 아래 행동하느냐**다.
자동화의 속도는 중요하지만, 운영 시스템에서 진짜 품질은 권한 설계의 정교함으로 결정된다.

OpenClaw를 잘 쓰는 팀일수록 모델 성능보다 먼저 권한 경계부터 설계한다.
그게 결국 사고를 줄이고, 신뢰를 쌓는 가장 빠른 길이다.
